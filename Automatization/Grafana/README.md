# Grafana

Single centralised Grafana instance (one instance, several folders/projects) that reads Prometheus from `Automatization/Monitoring/Prometheus` over the shared `monitoring-net` network.

## Architecture

Two roots are involved, and each one has a fixed job:

- `${PATH_TO_COMPOSE}` — a **clone of this repository kept on the server**. What the stacks only *read* lives here and is bind-mounted with absolute paths, which is the one bind form Portainer CE resolves (relative `./...` binds from the git clone resolve to an empty directory because CE never materialises the repository). Two things are read from it:
  - the Grafana **scripts** (`Automatization/Grafana/scripts/` → `/scripts`),
  - the **device registry** (`Automatization/Monitoring/Devices/` → `/devices`).
- `${PATH_TO_CONTAINERS}` — the data root. What the stacks *write* lives here: `Grafana/provisioning` (generated here) and `Grafana/data`. The same rule already used by the monitoring stack.

The clone is updated with `git -C "${PATH_TO_COMPOSE}" pull` and the stacks are redeployed (Portainer **Update**). Never run `git clean -fdx` or `git push -f` inside it: the live device `.env` files are untracked by design and live exactly there.

## Provisioning

A one-shot `bootstrap` service (`python:3-alpine`, `depends_on: service_completed_successfully`) generates the provisioning on every update into `${PATH_TO_CONTAINERS}/Grafana/provisioning`:

- **Prometheus datasource** — `datasources/prometheus.yml`: uid `prometheus`, url `http://prometheus:9090` (resolved through `monitoring-net`). Seeded **only if missing/empty**, so server-side edits survive.
- **Provider** — `dashboards/dashboards.yml`: the `Infrastructure/` folder, `file` type, `updateIntervalSeconds: 30`. Seeded only if missing/empty.
- **One dashboard per device** — `dashboards/devices/<uid>.json`, **always regenerated** (stale files are removed first, so removing a device removes its dashboard). Title and uid come from `DEVICE_NAME`; the *Host* variable is pinned to that device; the Battery and NVIDIA GPU rows are rendered only when `DEVICE_BATTERY`/`DEVICE_GPU` are `1`.

> The dashboard content is generated by the committed scripts (`bootstrap.py`, `dashboard.py`, `panels.py`). There is no hand-edited `grafana/provisioning/` folder in the repository; the classic `server-overview.json`/`client-1-overview.json` dashboards are retired and deleted by the bootstrap if still present.

> **The `host` label comes from Monitoring, not from Grafana.** The dashboards filter on `host="$host"`; that label is attached by the Monitoring bootstrap from each device's `DEVICE_NAME` when it writes `targets/nodes.yml`. If a device is UP in Prometheus but its dashboard shows no data, its target has no `host` label.

## Devices

The device registry `Devices/` is the single source of what is scraped and rendered. The live registry lives inside the server clone at `${PATH_TO_COMPOSE}/Automatization/Monitoring/Devices/<device>/.env`; the whole `Devices/` folder is gitignored, so no device names leak into the public repository. The committed reference copy is `Automatization/Monitoring/Devices.example/` (a `README.md` plus `example/.env.example`).

A device entry looks like:

```env
DEVICE_NAME="My Laptop"      # dashboard title, uid and the host label
DEVICE_ADDR=<ip>:9100              # where Prometheus scrapes node_exporter
DEVICE_BATTERY=1                   # render the Battery row only when set
DEVICE_GPU=0                       # render the NVIDIA row only when set
```

`DEVICE_NAME` must match `[A-Za-z0-9 ._-]`; the bootstrap aborts the stack otherwise. Adding/removing/renaming a device is adding/removing/editing one `.env` file in the clone and hitting Update on the stacks.

## Dashboards

`Infrastructure/` holds one overview per device, not per role. Every panel filters on `job="node"` and `host="$host"`, and the *Host* variable is pinned to the device, so the variable does not switch dashboards — each dashboard already is one device.

Base panels cover uptime, reboots, CPU, load, memory and swap, network traffic, disk I/O, filesystem usage and temperature. The Battery row (level, health, cycle count, power draw, AC source) appears only when the device has a battery and `DEVICE_BATTERY=1`. The NVIDIA GPU row appears only when `DEVICE_GPU=1`.

### Reading the panels

A few of these are easy to misread, and the misreadings are not obvious.

**`eth0 rx` and `eth0 tx` are one interface, not two.** Each interface produces two series, one per direction, with the legend `<device> rx` and `<device> tx`. Three interfaces show six lines. The panel is not hardcoded per device: it plots whatever the exporter reports, minus an exclusion regex, so a device that is missing means the exporter did not report it.

**A wired interface showing a flat `0.0 B/s` is usually just unplugged.** A laptop on WiFi still exposes its Ethernet NIC, and it still exports counters, all of them zero. An interface at exactly zero is a dormant interface, not a broken collector.

**The CPU legend shows the device name, not the address.** The panel aggregates with `avg by (host)` and the legend is `{{host}}`. Grouping by `instance` instead makes the legend the scrape address, which on a remote device is an overlay IP: redundant (each dashboard is already pinned to one device), confusing, and a real address of yours pasted into screenshots.

**Disk I/O hides the stacked layers on purpose.** The kernel counts the same I/O at every layer of a storage stack. On a typical Linux box a single write to the root filesystem is counted by the partition (`nvme0n1p3`), by the disk mapper device above it (`dm-0`) and by the physical disk (`nvme0n1`) — three series with identical values, which reads as three disks doing three times the work. The panels therefore filter out mapper devices, software RAID, loop devices, partitions and optical/removable nodes, keeping the physical disk plus memory-backed block devices like `zram`:

```
device!~"loop.*|ram.*|dm-.*|md.*|sr.*|fd.*|.*p[0-9]+$"
```

If you need per-partition detail, remove `.*p[0-9]+$` and remember you are reading a slice of the same bytes as the disk above it.

**The Temperature panel hides `pci0000:*` chips.** Those labels are PCI bus addresses, not product names, and what sits behind one depends on the hardware. An unlabelled BDF next to `k10temp` and `amdgpu` reads like a product. The mapping for the rest is in [the helper README](../Monitoring/node-exporter/README.md#sensor-names-in-the-panels): `k10temp` is the AMD SoC, `amdgpu` the integrated GPU, `nvme` the drive, `ath10k_hwmon` the WiFi card.

**The GPU row is the only temperature reading about the discrete GPU.** A discrete NVIDIA card normally has no hwmon chip at all, so it cannot appear in `node_hwmon_temp_celsius` however complete that panel looks. Temperature, utilisation, VRAM, power draw, clocks, PCIe link, throttle reasons and heartbeat gaps all come from the [GPU heartbeat](../Monitoring/node-exporter/README.md) instead, and the worst-gap series in the same row is the only record of how long the machine was hard-frozen. **The row is empty until the heartbeat timer is actually firing:** `systemctl list-timers nvidia-gpu-heartbeat.timer` has to show a `NEXT` and a `LAST`, not dashes. On a machine with no NVIDIA GPU the row is absent (no `DEVICE_GPU` flag).

## Data and secrets

- Persistence: `${PATH_TO_CONTAINERS}/Grafana/data` (never committed).
- Database: the project's MariaDB on `db-net`, connection details supplied through Docker secrets using `*_FILE` (`${PATH_TO_SECRETS}/Grafana/grafana_db_*`). Kept out of the repository.
- `user: "472:472"` (the grafana user), already compatible.

## Networks

- `db-net` (external) — MariaDB.
- `monitoring-net` (external) — Prometheus. Both must exist before deploying.

## Ports and access

- Host: `3001:3000` (port 3001 on the server). First login: `admin / admin` — change it afterwards.

## Deployment

> Before the first deploy, the server needs a persistent clone of this repository so the bootstrap can read the scripts and the device registry. This is a deliberate exception to the usual "nothing is read from the clone": a persistent clone is the one way CE lets a stack reach repository files, because the git-clone binds (`./...`) are the ones that resolve to nothing.

1. Clone the repository on the server: `git clone <repo> "${PATH_TO_COMPOSE}"`. It is a **read-mostly** clone: `git pull` to update, and the stack updates redeploy.
2. Create the live device registry in it: `${PATH_TO_COMPOSE}/Automatization/Monitoring/Devices/<device>/.env` for each machine, from the [template](../Monitoring/Devices.example/) (`DEVICE_NAME`, `DEVICE_ADDR`, `DEVICE_BATTERY`, `DEVICE_GPU`). The battery/GPU flags are per machine.
3. Deploy/update via Portainer → Grafana stack → **Update** (keep the existing variables and secrets). Stack environment variables: `PATH_TO_CONTAINERS`, `PATH_TO_SECRETS`, `PATH_TO_COMPOSE`.
4. `bootstrap` runs first (generates the provisioning, exits 0) and then `grafana` is recreated; `data/` and the secrets persist.

## Rolling update

1. `git push` the changes in `Automatization/Grafana/` (and `Automatization/Monitoring/` if the registry convention changed).
2. On the server, `git -C "${PATH_TO_COMPOSE}" pull`.
3. Portainer → Grafana stack → **Update**.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Dashboards do not appear | Provisioning not mounted | `docker inspect grafana` must show a bind on `/etc/grafana/provisioning`; if missing, Update the stack; if present but empty, check the `bootstrap` log, then `docker restart grafana` |
| `bootstrap` exited non-zero | Missing/empty device registry, or invalid `DEVICE_NAME` | `docker logs bootstrap`; create the `Devices/` entries in the server clone or fix the name (allowed: `[A-Za-z0-9 ._-]`) |
| A whole device has no dashboard | Its `.env` is missing from the registry | Create `${PATH_TO_COMPOSE}/Automatization/Monitoring/Devices/<device>/.env` and Update |
| Datasource error | Grafana cannot reach `prometheus` | Check that Grafana is on `monitoring-net` (`docker inspect grafana`) and that the network exists |
| Panels show `No data` for one device | The target has no `host` label, or the target is down | Check `/api/v1/targets` in Prometheus; if it is UP, the device entry is missing `DEVICE_NAME` |
| One panel is blank while its legend lists values | The series exists and is flat at zero, not a broken query | An idle machine is the usual answer. Confirm with `rate(node_disk_read_bytes_total{host="<name>"}[5m])`; no series at all means the collector failed, so check `node_scrape_collector_success` |
| The GPU row is absent on a machine that has an NVIDIA card | `DEVICE_GPU` is not `1`, or the row renders but is empty | Set the flag; if the row is empty, `systemctl list-timers nvidia-gpu-heartbeat.timer` must show a `NEXT` — a timer with only `OnUnitActiveSec` and no `OnActiveSec` schedules nothing on a fresh boot |
| Battery row does not appear despite the flag | The device has no battery exposed to `powersupplyclass` | `curl -s localhost:9100/metrics | grep ^node_power_supply_` on that device; nothing there means no battery is reported |
| A panel legend shows a raw IP address | The panel groups by `instance` instead of `host` | Legends should use `{{host}}`; the dashboard title already shows the device |
| `network monitoring-net not found` | The external network does not exist | Create it once: `docker network create monitoring-net` |
